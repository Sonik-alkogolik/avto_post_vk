# План разработки для 1 сообщества VK

## Цель этапа
На этом этапе разрабатывается **базовая архитектура под одно сообщество** и подготавливается процесс, по которому потом будут подключаться остальные сообщества.

Этот документ не про массовое подключение всех групп сразу, а про:
- разработку первого рабочего профиля сообщества;
- фиксацию структуры проекта;
- определение критериев завершения этапов;
- определение, куда и как добавлять HTML следующих сообществ.

---

## Общая логика проекта
Проект разбивается не по принципу «сразу все сообщества», а по принципу:

1. **Этап 1 — базовая разработка движка под 1 сообщество**
2. **Этап 2 — стабилизация и тестирование**
3. **Этап 3 — подключение новых сообществ как отдельных профилей**
4. **Этап 4 — UI, журналирование, статусы, масштабирование**

То есть HTML следующих сообществ ты присылаешь **не в рамках первого этапа ядра**, а в рамках **отдельного этапа подключения новых профилей**.

---

## Ответ на главный вопрос
### Куда присылать следующий HTML сообщества
Следующий HTML нужно присылать **в отдельном подэтапе подключения нового сообщества**.

Правильная модель такая:
- сначала делается **1 эталонное сообщество**;
- потом для каждого нового сообщества создаётся **отдельный профиль**;
- HTML нового сообщества добавляется в работу тогда, когда начинается этап **«Подключение сообщества №2 / №3 / №4»**.

### Значит ли это, что это уже другой этап?
**Да.**

Это уже не этап разработки ядра, а этап:
**«Сбор и подключение профилей новых сообществ»**.

---

# Этапы разработки

## Этап 1. Разработка базового ядра под 1 сообщество
### Цель
Сделать основу проекта, которая умеет работать с одним вручную описанным сценарием.

### Входные данные
- URL одного сообщества;
- HTML элементов этого сообщества;
- порядок шагов по форме;
- один текстовый шаблон;
- один путь к изображению.

### Что должно быть разработано
- структура проекта;
- профиль одного сообщества;
- последовательность шагов сценария;
- статусы шагов;
- журнал выполнения;
- базовый тест открытия и прохождения первого сценария.

### Что считается выполнением этапа
Этап считается выполненным, если:
- есть рабочее описание профиля одного сообщества;
- есть реализованный сценарий для него;
- есть тест, подтверждающий базовое прохождение;
- есть отчётный Markdown-файл;
- всё зафиксировано в Git.

### Артефакты этапа
- профиль первого сообщества;
- тест первого сообщества;
- отчётный `.md` файл;
- commit и push.

---

## Этап 2. Тестирование и стабилизация первого сообщества
### Цель
Понять, что сценарий не просто написан, а проходит основные шаги стабильно.

### Что делается
- проверяются ключевые шаги;
- фиксируются хрупкие места;
- уточняются проверки результата;
- обновляется профиль сообщества;
- усиливается тест.

### Что считается выполнением этапа
- сценарий проходит основные точки без случайных сбоев;
- ошибки распознаются и пишутся в журнал;
- тест показывает понятный статус;
- профиль сообщества уточнён.

### Артефакты этапа
- обновлённый профиль;
- обновлённый тест;
- новый `.md` отчёт;
- новый commit.

---

## Этап 3. Подключение следующего сообщества
### Цель
Добавить второе сообщество не переписывая ядро, а создавая новый профиль.

### Что от тебя нужно на этом этапе
Когда начинается этап подключения нового сообщества, ты присылаешь:
- название сообщества;
- ссылку;
- последовательность шагов;
- HTML кнопок и полей;
- финальный шаг отправки;
- описание, что считать успешным результатом.

### Что делается в разработке
- анализируется HTML нового сообщества;
- создаётся новый профиль;
- определяется, совпадает ли сценарий с уже существующим;
- если нет — добавляется отдельный сценарный тип;
- пишется/обновляется тест под новое сообщество.

### Что считается выполнением этапа
- новое сообщество описано как отдельный профиль;
- профиль встроен в общую систему;
- тест подтверждает базовую совместимость;
- изменения зафиксированы в Git.

### Артефакты этапа
- профиль сообщества №2;
- тест или расширение тестов;
- отчётный `.md` файл;
- commit и push.

---

## Этап 4. Развитие UI и журналирования
### Цель
Сделать удобный интерфейс контроля выполнения сценариев.

### Что делается
- добавляются чекпоинты этапов;
- показываются статусы;
- выводится текущее сообщество;
- выводится текущий шаг;
- отображаются ошибки и журнал событий.

### Что считается выполнением этапа
- UI показывает ключевые состояния;
- оператор видит, на каком шаге процесс;
- результаты фиксируются и не теряются.

---

# Как теперь правильно работать с HTML новых сообществ

## Не смешивать всё в один этап
Следующий HTML не нужно просто «досыпать» в первый документ как попало.

Правильно делать так:
- базовое ядро разрабатывается на 1 сообществе;
- потом начинается отдельная задача: **подключение нового сообщества**;
- в рамках этой задачи ты присылаешь HTML именно нового сообщества.

## Что ты присылаешь для нового сообщества
Для каждого нового сообщества лучше присылать не просто HTML-кусок, а пакет данных:

### Шаблон передачи данных
```md
# Новое сообщество

**Название:** ...  
**URL:** ...

## Шаги вручную
1. ...
2. ...
3. ...

## HTML кнопки открытия формы
...

## HTML поля текста
...

## HTML загрузки изображения
...

## HTML финальной кнопки
...

## Что считать успешным результатом
...

## Что считать ошибкой
...
```

---

# Что именно считается завершённым результатом на каждом этапе

## 1. После написания кода должен быть тест
Это обязательно.

### Этап считается завершённым, если тест подтверждает:
- страница открывается;
- сценарий стартует;
- форма открывается;
- базовые элементы доступны;
- сценарий доходит до целевой контрольной точки.

Тест нужен не «для галочки», а как доказательство, что код реально работает.

---

## 2. Должен создаваться Markdown-файл по дате
### Правило имени файла
- `22.04.2026.md`
- если уже есть файл за дату: `22.04.2026_v1.md`
- следующая версия: `22.04.2026_v2.md`

### Что должно быть внутри
- дата;
- текущий этап разработки;
- что было реализовано;
- что протестировано;
- результат теста;
- проблемы;
- следующий шаг.

### Когда этап считается выполненным
- файл реально создан;
- файл содержит итоги работы;
- файл добавлен в Git.

---

## 3. Всё должно быть зафиксировано в Git
### Минимум
- изменения добавлены;
- создан commit с понятным смыслом;
- изменения отправлены в удалённый репозиторий.

### Когда этап считается выполненным
- commit существует;
- push выполнен;
- история отражает завершённый кусок работы.

# Рекомендуемая последовательность разработки прямо сейчас

## Сейчас
Текущий этап: **разработка ядра под 1 сообщество**.

### Что должно быть сделано сейчас
1. оформить профиль первого сообщества;
2. описать шаги сценария;
3. определить критерии успеха;
4. определить критерии ошибки;
5. подготовить тест;
6. оформить отчётный `.md` файл;
7. зафиксировать всё в Git.

## Потом
Когда первый профиль стабилен, начинается новый этап:
**подключение второго сообщества**.

И вот тогда ты присылаешь следующий HTML.

# Definition of Done для текущего этапа
Текущий этап считается завершённым, если:
- есть рабочий профиль одного сообщества;
- шаги сценария описаны и реализованы;
- есть тест базового прохождения;
- создан Markdown-файл отчёта по дате;
- всё зафиксировано в Git и отправлено в удалённый репозиторий.

---

# Definition of Done для этапа подключения нового сообщества
Этап подключения нового сообщества считается завершённым, если:
- получен HTML и описание шагов нового сообщества;
- создан отдельный профиль;
- профиль встроен в проект;
- тест подтверждает базовую совместимость;
- создан новый Markdown-файл;
- изменения зафиксированы в Git.

---

# Короткий вывод
Сейчас следующий HTML **не нужно смешивать с первым этапом разработки ядра**.

Правильная схема такая:
- **этап 1** — сделать ядро и профиль первого сообщества;
- **этап 2** — стабилизировать и протестировать;
- **этап 3** — отдельно подключать новые сообщества, и вот туда ты уже присылаешь новый HTML.

---

# Git-фиксация после реализации этапа
После завершения каждого этапа результат обязательно фиксируется в Git и отправляется в удалённый репозиторий.

## Если репозиторий создаётся с нуля
```bash
echo "# avto_post_vk" >> README.md
git init
git add README.md
git commit -m "first commit"
git branch -M main
git remote add origin https://github.com/Sonik-alkogolik/avto_post_vk.git
git push -u origin main
```

## Если репозиторий уже существует локально
```bash
git remote add origin https://github.com/Sonik-alkogolik/avto_post_vk.git
git branch -M main
git push -u origin main
```
